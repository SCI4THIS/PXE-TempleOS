# RPI3B+PXE

RPI3B+PXE turns a Raspberry Pi 3B (or another Debian/Ubuntu host) into a LAN PXE server. `start.sh` is the entry point: it installs host dependencies, opens a terminal UI, manages NFS exports and media, generates the iPXE menu, and reconciles the Docker Compose services.

The server can boot Alpine Linux, install or run Omarchy over the network, repair an Omarchy installation that cannot boot with Limine, and launch TempleOS through a tailored Alpine/QEMU environment. Optional Samba and Tiny Core support are also included.

## How it works

The boot path is deliberately small at the DHCP/TFTP stage:

1. The machine's existing DHCP server assigns its address.
2. `dnsmasq` acts as a proxy-DHCP/PXE server and supplies a tracked iPXE image over TFTP.
3. iPXE chains to the menu generated by `start.sh`.
4. nginx serves kernels, initramfs images, overlays, and local media over HTTP.
5. NFS supplies Omarchy installer files and diskless roots where needed.

The Compose stack contains:

- `dnsmasq`: proxy-DHCP and TFTP. It does not replace the LAN's normal DHCP server.
- `http`: nginx web server and 30-day Alpine package cache.
- `samba`: optional writable share used by the Alpine development/QEMU flow.

The services use host networking, so the host must be on the same broadcast network as PXE clients and ports 67/UDP, 69/UDP, and 80/TCP must be available. NFS must also be reachable by clients. The project assumes trusted LAN use; do not expose these services directly to the internet.

## Quick start

Clone the repository, including the pinned iPXE source submodule, then start the UI:

```bash
git clone --recurse-submodules https://github.com/SCI4THIS/RPI3B-PXE.git
cd RPI3B-PXE
./start.sh
```

On first launch, the script checks for `whiptail`, Docker Compose, wget, xorriso, rsync, and the NFS server tools. On an apt-based system it offers to install missing packages and enable Docker and NFS. It uses `sudo` for host configuration when not already running as root.

The first run creates `${XDG_CONFIG_HOME:-$HOME/.config}/rpi3b-pxe/config.env`. Defaults are shown in `config.env.example`. Normally, change them through the NFS, Samba, and Backup screens instead of editing generated files. The default storage layout is under `/mnt/ssd`; configure those paths before downloading large media if that is not appropriate for the host.

From the main menu, choose **Start / reconcile PXE services**. This applies NFS exports, creates the iPXE menu and rescue overlay, builds changed container images, and starts the selected services. Subsequent starts use input hashes to avoid unnecessary rebuilds.

## Boot options

Entries only appear when their required server-side files are ready.

- **Alpine Linux**: unmodified Alpine netboot, with x86-64 and 32-bit x86 selected according to the client CPU.
- **Alpine Linux - Development**: available when Samba is enabled; provides the QEMU build environment used by the TempleOS flow.
- **Temple OS**: boots Alpine and launches TempleOS under the custom QEMU package. Download its ISO from the TempleOS screen first.
- **Omarchy - Install**: boots the Omarchy installer using kernel/initramfs files over HTTP and the extracted ISO tree over NFS.
- **Omarchy - NFS**: boots a prepared Omarchy installation from a shared, read-only NFS root with a temporary RAM OverlayFS; `/home` remains on a persistent read-write NFS export.
- **Omarchy - Boot Repair**: standalone recovery UI for replacing a broken Limine legacy-BIOS setup with GRUB.
- **Tiny Core Linux**: shown after `scripts/download-tinycore.sh` has populated the local web root.
- **iPXE shell**: interactive network-boot diagnostics.

## Omarchy support

### Network installer

Open **Omarchy > Manage Omarchy installer media > Download**. `start.sh` downloads the configured Omarchy release, verifies its pinned SHA-256 digest, extracts `/arch`, refreshes NFS, and adds **Omarchy - Install** to the PXE menu. The installer does not need to fetch the ISO independently on every client.

The default supported release is currently `4.0.1`. A different `OMARCHY_VERSION` also requires adding its trusted digest to `start.sh`.

### Diskless Omarchy over NFS

This mode turns an installed x86-64 Omarchy system into a reusable network root:

1. In `start.sh`, open **Omarchy > NFS** and enable the temporary build export. This briefly enables `no_root_squash`; restrict `PXE_NETWORK` correctly.
2. Copy `scripts/omarchy-nfs-stage.sh` and `scripts/omarchy-nfs-finalize.sh` to the installed Omarchy machine, keeping them in the same directory.
3. Run the command displayed by **Show NFS build instructions**. The staging script copies the system, installs NFS initramfs support, makes the image hardware-generic, and creates stable PXE kernel links.
4. Back on the server, choose **Promote finalized build to RO root**.
5. Disable the temporary build export immediately.

Clients then share an immutable NFS system tree. Changes outside `/home` live only in each client's RAM overlay and disappear at reboot; `/home` persists in the read-write export.

### Switching Limine to GRUB with PXE boot repair

Some legacy BIOS systems can complete an Omarchy installation but fail to boot through Limine. **Omarchy - Boot Repair** exists so the machine can recover without another rescue USB: PXE supplies an Alpine environment, all required disk/encryption/GRUB tools, and the repair UI directly from this server.

The repair flow discovers the disk, FAT `/boot`, LUKS2 root, Btrfs `@` subvolume, installed kernel/initramfs, CPU microcode, and whether mkinitcpio uses `encrypt` or `sd-encrypt`. Ambiguous hook configurations are rejected instead of guessed. Use **Diagnostics** first, then **Dry Run** to inspect and validate the proposed `grub.cfg` and `grub-install` command. The **Commit** action requires two confirmations, backs up boot metadata and existing loader configuration, installs BIOS GRUB, and writes matching LUKS kernel arguments.

Automatic commit is intentionally limited to the tested **legacy BIOS + MBR/dos + FAT `/boot` + LUKS2 + Btrfs `@`** layout. UEFI and GPT targets can be diagnosed but are refused for writes. See [`docs/omarchy-boot-repair.md`](docs/omarchy-boot-repair.md) for the exact workflow and safety boundaries.

## Repository layout

```text
start.sh                 Main installer, configuration UI, and orchestrator
docker-compose.yml       Base dnsmasq/nginx/Samba service definitions
compose.runtime.yml      Host storage and generated-runtime mounts
dnsmasq/                 TFTP server, tracked iPXE binaries, pinned source
nginx/                   Web image, active config, overlays, and working data
samba/                   Optional development share image
scripts/                 iPXE build, Tiny Core, and Omarchy NFS utilities
docs/                    Detailed operational documentation
```

Generated configuration and boot menus live under the user's XDG config directory. Downloaded media and promoted NFS roots live in configured export directories. `nginx/www` is working/cache data and is not source-controlled.

## Rebuilding iPXE

Prebuilt iPXE artifacts are committed so the Raspberry Pi does not need an x86 cross-compiler. After intentionally updating the `dnsmasq/ipxe-src` submodule, rebuild them on an x86-64 development host:

```bash
./scripts/build-ipxe-artifacts.sh
```

The script builds from a disposable copy, writes artifacts beneath `dnsmasq/tftp`, and records their source revision and SHA-256 digests in `dnsmasq/tftp/ipxe-build.txt`. Review and commit those generated changes.

## Operations and troubleshooting

- Re-run `./start.sh` for all normal management. The `--tui` flag skips the dependency bootstrap and is mainly used internally after installation.
- **Monitor Docker Compose** follows recent logs; Ctrl+C returns to the menu.
- **NFS > Apply / repair NFS exports** recreates the managed exports file at `/etc/exports.d/rpi3b-pxe.exports`.
- The backup screen mirrors the read-write export to the configured server-only backup directory. It does not back up the read-only media export.
- If PXE is not offered, check that the client and server are on the same LAN, network boot is enabled in firmware, and no firewall or other PXE service is occupying the required ports.
